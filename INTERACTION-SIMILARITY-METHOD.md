# Interaction-pattern nearest-neighbor method

Status: **nearest-neighbor score implemented and tested on synthetic vectors; fingerprint generation and real-data calculations remain unresolved**. This audit concerns the ligand–protein interaction pattern, not a ligand-free structural alignment of binding pockets. It is intended to provide one nearest training complex for each evaluation complex, for subsequent exploratory comparison with frozen RF-Score prediction errors.

## Paper comparison

The [LP-PDBBind journal article](https://pmc.ncbi.nlm.nih.gov/articles/PMC13430955/) computes a 256-component integer-valued proteo-chemometric interaction fingerprint based on ligand atom environments and nearby protein residues, then compares fingerprint vectors using weighted Jaccard similarity. Its Figure 1 reports distributions of the *maximum* interaction similarity from each validation or test complex to the training set. The paper therefore already performed this nearest-neighbor similarity analysis; our calculation is an audit on our exact frozen cohorts, not a new nearest-neighbor concept.

The paper cites [Wang, Xie and Yan's proteo-chemometric IFP](https://doi.org/10.1093/bioinformatics/btab132), whose [IFPscore toolkit](https://github.com/debbydanwang/IFPscore) is available. This does not by itself establish which version, fingerprint options, preprocessing, and structure preparations LP-PDBBind used. The upstream LP-PDBBind README describes its similarity notebook as computing **protein sequence and ligand** similarities; we have not located an author implementation of the interaction-fingerprint calculation. On 2026-11-18 we rechecked the publisher supplement supplied by the user (`jp5c08598_si_001.pdf`, SHA-256 `2c565ab2aa60e94bc750852e60557413c525855dd11269cc9b8248a7e667f1ad`). Its similarity-method section covers proteins and ligands; Figures S2–S3 mention interaction-fingerprint similarities but the extracted text does not specify their construction settings. The journal main text supplies the 256-component representation and formula, but this is not enough to verify exact historical generation.

## Intended paper-aligned calculation

1. Restore the frozen baseline membership and structure files. Use its 7,393 training complexes as the reference candidates; query validation (958), internal test (2,171), and BDB2020+ (115) separately. Preserve cohort membership, complex identifiers and hashes for each structure input. Cohort sizes are expected, not successful-fingerprint counts.
2. Resolve and pin the fingerprint implementation, exact version, options, ligand and protein preparation, contact definitions, and 256-component integer-vector construction against the paper and author code where possible. Validate a small set of inputs, inspecting failed and empty fingerprints; do not silently substitute zero vectors. **These details are not resolved, so this is not yet an executable paper-exact protocol.**
3. Generate a vector `X` for each usable query and training complex using the same fixed implementation and preprocessing. For each query compare against every usable training complex `Y` using the published weighted Jaccard formula:

   `similarity(X,Y) = sum_i min(X_i,Y_i) / sum_i max(X_i,Y_i)`.

   If the denominator is zero, mark the comparison undefined. Report missing/failed inputs and eligible candidate counts instead of assigning similarity zero or one.
4. Select the training complex with the maximum defined score. Record all tied IDs, or a deterministic lexicographically selected ID with the full tie count; retain the actual nearest score, query and neighbor IDs, input/cohort metadata, validity status, software and parameters. If no valid candidate exists, report no neighbor.
5. Validate the implementation using identical and disjoint nonzero synthetic vectors, symmetry and undefined empty-vector cases; verify the maximum against brute-force comparisons on a small sample. Audit fingerprint generation itself against the authors' method and example structures before interpreting results.

## Implemented score and remaining prerequisite

[`scripts/interaction_nearest.py`](scripts/interaction_nearest.py) calculates the maximum published weighted Jaccard score from **precomputed** count vectors. It takes separate CSV files with header `id,f000,...,f255`, integer nonnegative counts, and excludes invalid and all-zero vectors with an audit record. It uses exact rational comparisons for ties and chooses the lexicographically first training ID as representative. [`tests/test_interaction_nearest.py`](tests/test_interaction_nearest.py) checks score arithmetic, ties, exclusion, and undefined empty-vector comparisons; three tests pass in the project's isolated environment. Input fingerprint files and generation parameters are not supplied by this script. The original PDBbind and BDB2020+ structures and frozen runs were found in the sibling `binding_affinity_v2` checkout, but the existence of structures does not resolve the historical fingerprint settings or ensure coordinate preparation matches the paper. No real-data run is claimed.

The score formula and maximum-over-training strategy match the paper at the published description level. **The full calculation is not yet verified to match the paper**, because construction settings, structure provenance and implementation remain unresolved. Our exact training subset may also differ from the reference set underlying Figure 1. Do not label a discrepancy a split violation without reconciling these differences.

## Follow-up: cited toolkit and executable feasibility

On 2026-11-18, we inspected the complete tree of the pinned LP-PDBBind repository (`cc363f80a6a696d562f290a87aa20173e60f6c52`); it does not identify a dedicated interaction-fingerprint generator or saved interaction vectors. We searched source cells in its similarity, splitting, and information-preparation notebooks for interaction-fingerprint and related implementation names and found no matches; this targeted search is not proof that no related code exists anywhere. The cited [IFPscore implementation](https://github.com/debbydanwang/IFPscore/tree/a138dd4b417dc3638100debc97e7ccc6d65e940d) is a plausible starting point, not evidence that LP-PDBBind used the exact example settings. The linked commit predates the journal article; current main `9219260a815698a5c0a7396cebb25fe49fe6cc4b` adds a license in 2026. The [PrtCmm example](https://github.com/debbydanwang/IFPscore/blob/a138dd4b417dc3638100debc97e7ccc6d65e940d/Examples/PrtCmmIFPScore.py) specifies the classic ECFP algorithm, radii `[1, 1]`, a `(0, 4.5)` Å contact bin, heavy atoms, atomic-number/connectivity/hydrogen-count/formal-charge properties, count folding and powers 7, 8 and 9. The [implementation](https://github.com/debbydanwang/IFPscore/blob/a138dd4b417dc3638100debc97e7ccc6d65e940d/IFP.py) folds protein and ligand identifiers separately and concatenates them: the example's power 7 produces **two 128-component blocks**, or 256 total. Power 8 would instead produce 512 for this ECFP mode. Other settings and fingerprint types exist, so the journal's 256-dimensional description does not establish that power 7 or any particular example configuration was used.

The toolkit README calls for Linux/Python 3.6, DeepChem, RDKit, Biopython and SciPy, and says PDBbind ligands must be saved as PDB files. The available sibling checkout instead contains the original SDF/MOL2 ligand structures, and its isolated environment lacks DeepChem and `pickle5`. The toolkit also writes selected chain PDB files and cached solid-angle pickles beside input paths during initialization; a safe trial requires copies in a writable scratch directory, never the original licensed files. Its chain selection and unconditional solid-angle calculation are further preparation details to audit. Neither the exact LP-PDBBind version and options nor the SDF/MOL2-to-PDB conversion is documented by these findings.

### Exploratory three-structure feasibility trial

We ran the 2021 IFPscore example settings above on copies of 6fhu, 6fhq and 6mj7, chosen among the smallest refined-set proteins to reduce trial cost. RDKit 2026.03.6 converted their SDF ligands to PDB. The atom and bond **counts** were unchanged for all three; coordinate rounding was at most 0.0005 Å. This check did not verify bond orders, charge, stereochemistry, or full chemical equivalence.

The original toolkit did not run unchanged. The approved DeepChem 2.5.0 installation requires unavailable TensorFlow at package import and renamed the legacy modules used by IFPscore. For this scratch-only trial we used the actual DeepChem 2.3.0 `rdkit_util.py` loader source, loaded without the full package, and replaced unused string-hash imports with functions that raise if called; the example used `hash_type='vec'`. Python's standard `pickle` supplied the `pickle5` import. NumPy 2.2.6 rejected `self.Triangles != []` in the toolkit's solid-angle code; changing this single scratch-copy condition to `len(self.Triangles) != 0` allowed the sample to run. These adapters and the toolkit copies were placed under `/private/tmp/ifp-trial`; the installed dependency is in `/private/tmp/ifpscore-deps`. Original structures were never modified.

Each sample produced a 256-component nonzero vector and repeat calculation within the same process was identical: sums/nonzero components were 173/52 (6fhu), 140/42 (6fhq), and 127/42 (6mj7). This is only an implementation feasibility smoke check on three small structures, without an author reference, independent-process repeatability or chemical validation. It does not establish that the adapters, converted inputs, fingerprint settings or results match LP-PDBBind. No cohort-wide or nearest-neighbor interaction result was produced.

The next concrete step is to build a pinned, isolated candidate toolkit environment without the temporary adapters, audit atom/bond/protonation preservation during conversion, validate independent-process repeatability and compare with an author-provided reference fingerprint if obtainable. Keep an explicit record of source commit, settings, hashes and failure coverage before any cohort-wide run.

## Other pocket and interaction measures

The earlier proposed ProLIF residue-type × interaction-type binary fingerprint with binary Tanimoto is **not the paper's interaction fingerprint**. It can be investigated later as a separate, coarse alternative, but it requires a fixed preparation protocol and cannot be interpreted as 3D pocket alignment. Similarly, 3D binding-pocket structural alignment measures a distinct property and is a later E08 comparison, not the calculation described above. Neither alternative is selected as the paper-reproduction method here. For later work, compare their ability to explain per-complex squared error and cohort RMSE with the paper-aligned similarity on the same eligible complexes, reporting coverage, uncertainty and the fact that these outcomes have already been inspected; no alternative is assumed superior.

No interaction similarities, neighbor identities, or similarity–error relationships have been computed in this audit.
