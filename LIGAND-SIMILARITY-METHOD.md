# Ligand nearest-training-neighbor method

Status: an initial paper-aligned audit has been calculated for all three evaluation cohorts; it is not an exact historical reproduction. The analysis compares each evaluation ligand with the frozen RF-Score training cohort. It does not measure prediction error by itself.

## Sources and agreement

The comparison target is the peer-reviewed 2026 journal article, DOI [10.1021/acs.jpcb.5c08598](https://doi.org/10.1021/acs.jpcb.5c08598), and its publisher supporting information. The latter was rechecked against the user-supplied file `jp5c08598_si_001.pdf` (SHA-256 `2c565ab2aa60e94bc750852e60557413c525855dd11269cc9b8248a7e667f1ad`). Pages S3–S4 specify RDKit 2023.3.2, ligand SMILES from PDBBind MOL2 files with SDF fallback, 1,024-bit Morgan fingerprints and Dice similarity, radius 2 initially, then radii 4 and 10 for apparent identical pairs, followed by a canonical-SMILES comparison. The paper reports distributions of maximum training-set similarity. The SI equation prints a union sign in the Dice numerator, but its accompanying prose specifies bits on in both fingerprints, and the author notebook implements RDKit Dice; this audit uses the intersection, not the literal printed union.

The pinned author [similarity notebook](https://github.com/THGLab/LP-PDBBind/blob/cc363f80a6a696d562f290a87aa20173e60f6c52/dataset_creation/calc_similarities.ipynb), code cell 17 (zero-based), reads `info.smiles` with `Chem.MolFromSmiles`, uses `AllChem.GetMorganFingerprintAsBitVect(mol, 2, nBits=1024)` and `DataStructs.DiceSimilarity`, then implements the radius-4, radius-10 and `Chem.MolToSmiles` checks below. Other fingerprint options are library defaults. This agrees with the publisher SI on the checked procedure, not a claim that the exact historical journal figure has been reproduced. The notebook uses `info.csv`; verify the provenance of the released metadata SMILES and whether they match the historical `info.csv` before reporting exact replication.

**Correction:** an earlier project discussion proposed starting at radius 4 and using SDF only. Neither matches the arXiv v3 description or the pinned notebook's primary similarity calculation.

## Calculation to implement

1. Restore the frozen baseline membership: 7,393 noncovalent CL1 training records; separately evaluate the 958 validation, 2,171 internal test, and 115 BDB2020+ records used by the baseline. Check identifiers and membership against the saved manifests, and record input hashes. Cohorts and input availability must be verified when restored.
2. For internal PDBBind, use the released ligand SMILES, after checking their provenance against the source `info.csv`. The authors describe deriving them preferentially from MOL2, falling back to SDF when MOL2 cannot be read. Parse using `Chem.MolFromSmiles` with RDKit 2023.3.2 and record defaults, input SMILES, canonical SMILES, software version, failures, and unusual multi-fragment cases. Do not silently replace a failed ligand with similarity zero or alter charges, salts, tautomers, or stereochemistry. For the initial audit below, BDB2020+ query SMILES are taken from the released benchmark CSV; their construction has not yet been reconciled with the authors' original comparison input.
3. Build 1,024-bit radius-2 Morgan bit vectors with `GetMorganFingerprintAsBitVect`, preserving the source implementation's defaults. For each query, compare against every valid training ligand using Dice similarity `2c/(a+b)`, where `a` and `b` count the on bits and `c` counts shared on bits. Treat fingerprints with no meaningful bits as failures and report them.
4. For every pair with radius-2 Dice exactly 1, recalculate using radius 4. If that score is exactly 1, recalculate using radius 10. If that score is still exactly 1 but `Chem.MolToSmiles` differs, set the score to 0.99. Use the last applicable score. Store the initial and final scores and escalation stage for audit. Apply these checks to **all** qualifying pairs before finding the maximum; adjusting only the preliminary winner could change which ligand is nearest.
5. The nearest training ligand is the one with the largest final score. Save query cohort and ID, neighbor ID, score, radius-2 score, comparison stage, number of tied maxima, and the number of valid training candidates. Break exact ties by lexicographic training ID for a single representative while retaining tie count. Keep failures and exclusions in a separate audit, including missing training entries, rather than confusing missing values with dissimilarity.
6. Validate identical molecules, distinct molecules with possible fingerprint collisions, stereoisomers, multicomponent structures, missing/invalid inputs and ties; compare bulk results with explicit pair calculations. Report coverage and inspect the handling of stereochemistry, chirality defaults, SMILES serialization and no-bit fingerprints before interpreting similarities.

Each selected maximum is an association with a training ligand; the closest ligand need not occur with the closest training protein. The paper's Figure 1 similarity comparisons use its stated split cohorts, which may not be identical to the frozen model's clean, noncovalent training set. BDB2020+ nearest-neighbor results must be labeled a separate audit. Differences in cohort, preparation, version, or source data can change scores; apparent threshold exceedances are not automatically evidence of leakage or author error.

## Initial audit (2026-11-18)

[`scripts/ligand_nearest_neighbor.py`](scripts/ligand_nearest_neighbor.py) implements the published radius-escalation and Dice rules against the frozen training membership. It used the released `LP_PDBBind.csv` SMILES and, for BDB2020+, the released benchmark CSV SMILES. The available isolated environment has RDKit **2026.03.6**, not the SI's 2023.3.2. Historical SMILES provenance and exact paper-figure cohort membership remain unverified; the files below are therefore exploratory, paper-aligned results, not an exact reproduction.

- [Validation neighbors](outputs/similarity/ligand-validation.csv): 958 of 958 query SMILES parsed.
- [Internal test neighbors](outputs/similarity/ligand-test.csv): 2,171 of 2,171 query SMILES parsed.
- [BDB2020+ neighbors](outputs/similarity/ligand-bdb2020.csv): 115 of 115 query SMILES parsed.

Nine of 7,393 training SMILES failed RDKit sanitization, leaving **7,384 candidates** per query. The corresponding audit JSON files list excluded IDs and record input/output hashes and RDKit version. No structure fallback or replacement was silently applied. Neighbor scores could change if those missing candidates can be validly reconstructed under the source protocol or under RDKit 2023.3.2. Exact ties are represented by the lexicographically first training ID and their count. Unit checks cover identical and different ligands, invalid inputs, and bulk-versus-scalar Dice; an exhaustive scalar comparison for validation complex `1a0q` confirmed the stored maximum, representative and tie count. No similarity–prediction-error analysis has been performed.

## RDKit version and input follow-up (2026-11-18)

An isolated conda-forge RDKit **2023.03.2** environment was created in `/private/tmp/ligand-rdkit2023` and verified via `rdBase.rdkitVersion`; its platform-specific package specification is [recorded](environment/ligand-rdkit2023-osx-arm64-explicit.txt). This matches the journal SI's RDKit version, but not necessarily the authors' complete software environment. Reusing the same released SMILES and frozen cohorts, **all 7,393 training ligands and all 3,244 evaluation ligands parsed**. The earlier nine failures therefore arise under the 2026 version for these inputs; do not silently replace them or assume they are invalid chemical records.

- [Validation, RDKit 2023](outputs/similarity/ligand-validation-rdkit2023.csv): 958 queries, all 7,393 training candidates.
- [Internal test, RDKit 2023](outputs/similarity/ligand-test-rdkit2023.csv): 2,171 queries, all 7,393 candidates.
- [BDB2020+, RDKit 2023](outputs/similarity/ligand-bdb2020-rdkit2023.csv): 115 queries, all 7,393 candidates.

Compared row by row with the 2026-version audit, two validation queries (`6idg`, `6kdi`) have a different maximum and representative: the 2023 result selects training ligand `4lhm` (0.5045045), which was excluded from the earlier run; the old representative was `3lxo` (0.4954128). No test or BDB2020+ maximum score, representative, or tie count changed. This comparison changes both RDKit version and candidate coverage, so it does not isolate a version effect on shared ligands. The three existing ligand unit tests passed under RDKit 2023.03.2; each result's companion audit records source and output hashes and coverage.

An exhaustive scalar check across all 7,393 candidates for `6idg` independently verified the saved maximum, representative and tie count under RDKit 2023.03.2.

The pinned author `prepare_info.ipynb` cell 7 constructs SMILES from PDBBind MOL2 first, falling back to SDF, and cell 9 places these in `df['smiles']`. This establishes the released code's intended preparation, not that our metadata column is byte-for-byte the historical `info.csv` used in the published analysis. As a targeted check, with RDKit 2023.03.2, the nine previously failing IDs' original MOL2 files all parse and produce the exact released SMILES for eight; `1wc1` produces a different charged, stereospecified SMILES, so its source history remains unresolved. No replacement was made.

For BDB2020+, the pinned `prepare_BDB2020+_dataset.ipynb` reads a `prepared.csv` reference SMILES, selects an extracted ligand by radius-2 Morgan/Dice, checks heavy-atom counts, and uses `AssignBondOrdersFromTemplate` to write its ligand SDF. The initial and 2023 audits use the *released BDB2020+ CSV SMILES* as query input, not a newly derived SDF SMILES. The linkage between that released CSV and the historical `prepared.csv` remains unverified, so label the BDB result a separate paper-aligned audit rather than an exact replication.
